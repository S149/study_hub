Chapter 1

Fundamentals of Testing

Software testing is a set of activities to discover defects and evaluate the quality of software work products — not only running code and checking results, but planning, analysis, design and reporting too. This chapter lays the groundwork: what testing is, why it exists alongside debugging and quality assurance, the seven principles every tester relies on, and the roles and skills that make testing effective.

1.1

What is Testing?

Software testing assesses software quality and helps reduce the risk of failure in operation. Two common misconceptions get in the way: that testing is only about executing tests, and that it only verifies a system against its specification. In fact testing also involves validation — checking that the system meets the real needs of users and other stakeholders in its operational environment. Testing can be dynamic (the software is executed) or static (it is not — reviews and static analysis, see chapter 3).

Evaluate work products

Requirements, user stories, designs, and code.

Cause failures, find defects

The most direct way to surface problems before users do.

Ensure required coverage

Reduce risk

Lower the risk level of inadequate software quality.

Verify requirements

Verify compliance

Inform decisions

Build confidence

In the quality of the test object.

Validate fitness for use

Confirm the test object works as stakeholders expect.

Objectives shift with context: the work product tested, the test level, risk, the SDLC in use, and business factors like time to market.

1.1.2 Testing and Debugging K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic, and can summarize, compare, classify, and give examples for the concept.

Testing and debugging are separate activities. Dynamic testing triggers a failure; debugging then finds and removes the defect behind it. When static testing is used, it finds the defect directly — no failure ever occurs, so there is nothing to reproduce.

01Reproduce the failureConfirm it happens reliably
→
02DiagnoseFind the defect causing it
→
03Fix the defectA non-testing activity
Note

Static testing skips straight to fixing: since it never executes the software, there is no failure to reproduce or diagnose — the defect is already in view.

Afterwards, not part of it

Debugging ends once the defect is fixed. Confirmation testing — ideally by the same person who ran the original test — is a separate, subsequent testing activity that checks whether the fix actually resolved the problem. Regression testing may follow it, to check the fix didn’t break anything else (see section 2.2.3).

1.2

Why is Testing Necessary?

Testing is a form of quality control: it helps achieve agreed test objectives within scope, time, quality and budget constraints — and every stakeholder, not only the test team, can contribute to that.

1.2.1 Testing’s Contributions to Success K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic, and can summarize, compare, classify, and give examples for the concept.

Cost-effective defect detection

Found defects can then be debugged, indirectly raising quality.

Quality evaluation across the SDLC

Feeds decisions such as whether to release.

Indirect user representation

Testers carry users’ needs into the development process.

Testing may also be required to meet contractual, legal or regulatory obligations.

Not every defect fails

Some defects always cause a failure when executed, some only in specific circumstances, and some never do. Failures can also come from environmental conditions alone (e.g. radiation flipping a bit in firmware) — with no defect involved at all.

Root cause

The fundamental reason a problem occurred. Root cause analysis, done after a failure or defect appears, aims to remove that cause so similar problems don’t recur.

1.3

Testing Principles K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic, and can summarize, compare, classify, and give examples for the concept.

Seven general guidelines apply across all testing, regardless of context.

  1. 1

    Testing shows the presence, not the absence, of defects

    It can prove defects exist, never that the object is defect-free.

  2. 2

    Exhaustive testing is impossible

    Except in trivial cases — use techniques, prioritization and risk to focus effort instead.

  3. 3

    Early testing saves time and money

    Defects removed early don’t cascade into later work products. Start static and dynamic testing as soon as possible.

  4. 4

    Defects cluster together

    A Pareto effect — a small number of components usually contain most defects or cause most failures.

  5. 5

    Tests wear out

    Repeating the same tests stops finding new defects — unless the point is automated regression testing.

  6. 6

    Testing is context dependent

    There is no single universal approach; testing is done differently in different contexts.

  7. 7

    Absence-of-defects is a fallacy

    A system can pass every specified test and still fail to meet real user needs and business goals — validation matters as much as verification.

4.2

Black-Box Test Techniques

4.2.1 Equivalence Partitioning (EP) K3K3: ApplyThe candidate can carry out a procedure when confronted with a familiar task, or select the correct procedure and apply it to a given context.

EP divides data into partitions where the theory holds that testing one value from a partition is representative of all of them — so one test per partition is enough. Partitions apply to inputs, outputs, configuration, internal values, timing, and interface parameters alike. Partitions must not overlap and must each be non-empty; a partition of valid values is a valid partition, one of invalid values an invalid partition — the trick in practice is defining both carefully.

The coverage items are the partitions themselves. Coverage = partitions exercised ÷ total partitions identified, so 100% coverage means every partition, including invalid ones, is hit at least once. When a test item has several sets of partitions (e.g. more than one input parameter), the simplest criterion is Each Choice coverage: exercise every partition of every set at least once, without worrying about combinations between sets.

4.2.2 Boundary Value Analysis (BVA) K3K3: ApplyThe candidate can carry out a procedure when confronted with a familiar task, or select the correct procedure and apply it to a given context.

BVA exercises the edges of ordered partitions, since implementation errors cluster at boundaries — misplaced by one, or missing entirely. 2-value BVA tests a boundary and its closest neighbor in the adjacent partition; 3-value BVA adds the value exactly on the boundary’s other side too, so it can catch defects (e.g. ≤ coded as =) that 2-value BVA overlooks.

2-value coverage = boundary values exercised ÷ total boundary values · 3-value coverage = (boundaries + neighbors) exercised ÷ total identified. Both reach 100% only once every coverage item for every boundary has been exercised.

Decision tables record how combinations of conditions map to actions — ideal for business rules. Columns are rules; coverage is the percentage of feasible columns exercised.

4.2.4 State Transition Testing K3K3: ApplyThe candidate can carry out a procedure when confronted with a familiar task, or select the correct procedure and apply it to a given context.

A state diagram models a system’s states and the valid transitions between them, each triggered by an event (and optionally a guard condition), written as event [guard] / action.

State table

The same model as a table: rows are states, columns are events (with any guard condition), and each cell holds the target state and resulting action. Unlike the diagram, a state table shows invalid transitions explicitly — as empty cells.

All states

Every state is visited at least once. The weakest criterion — achievable without exercising every transition.

Valid transitions (0-switch)

Every valid transition is exercised. The most widely used; full coverage here guarantees full all-states coverage.

All transitions

Every valid transition, plus an attempt at each invalid one — one per test case, to avoid defect masking. Guarantees both other criteria, and should be the minimum for mission- and safety-critical software.

White-box techniques are read from a control flow graph — the possible sequences in which code statements execute.

4.3.1 Statement Testing and Statement Coverage K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic, and can summarize, compare, classify, and give examples for the concept.

Coverage items are executable statements. Coverage = statements exercised ÷ total executable statements. 100% guarantees every statement ran at least once — but not that every decision outcome was tested.

4.3.2 Branch Testing and Branch Coverage K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic, and can summarize, compare, classify, and give examples for the concept.

Coverage items are branches — both conditional and unconditional transfers of control. Coverage = branches exercised ÷ total branches. Branch coverage subsumes statement coverage: 100% branch coverage guarantees 100% statement coverage, never the reverse.

4.3.3 The Value of White-box Testing K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic, and can summarize, compare, classify, and give examples for the concept.

Strength

Considers the whole implementation, so it finds defects even when the specification is vague, outdated or missing.

Weakness

Can’t detect a missing requirement — an omission that was never implemented leaves no code to cover.

Also static

Black-box testing alone gives no measure of actual code coverage. White-box coverage is an objective measurement that shows where to add tests, raising confidence in the code.

1.1

Testing in the Software Development Lifecycle K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic, and can summarize, compare, classify, and give examples for the concept.

The organization of test activities depends on the software development lifecycle (SDLC) being followed, so the TA’s involvement in test activities varies with the adopted SDLC model. A good practice common to all SDLC models is that the TA should be involved from the initial phases of the SDLC.

Sequential

Phased, little overlap

Development activities happen in phases, one starting after the previous completes. The TA’s tasks change over time: supporting test planning early, beginning test analysis once the test basis is produced, running test design and implementation in parallel with software design and implementation, then executing tests and supporting test completion in the late phases.

Incremental

Independent increments

Software is divided into smaller, manageable increments, each developed and tested independently. The TA repeats test analysis, design, implementation, execution, and test management support for each increment, focusing on new or modified features. Because regression risk increases, the TA pays particular attention to refactoring and to assembling regression test suites.

Iterative

Cyclical refinement

The project undergoes repeated cycles of prototyping, testing, refining, and deployment. The TA role is dynamic and adaptive, collaborating closely with developers and business representatives, adapting test conditions and test cases as the software evolves, and feeding back process improvements each iteration. The more frequent the iterations, the more critical ongoing regression test maintenance becomes.

Note

An SDLC may combine elements of several models and techniques — for example, Agile software development combines aspects of both iterative and incremental models. In such cases, the TA’s involvement depends on the SDLC’s specific characteristics and how they are combined.

During test analysis, the TA checks the completeness of the test basis and collects additional relevant information, including verbal information such as conversations in collaborative user story writing. Changes to the test basis can lead to adjustments to the test scope, coordinated with test management.

Before proceeding, the TA checks entry criteria: test planning has been performed and the test scope, objectives, and approach are clear; the test basis (requirements, user stories, etc.) is defined; and identified product risks have been evaluated and documented if required.

The TA evaluates the test basis to identify defects and assess testability, giving early feedback to product owners — this may include modeling system behavior for the test techniques to be applied, and applying review techniques. Undocumented defects in the test basis must be recorded if not directly fixed. The TA also determines the test oracles needed.

The TA defines and prioritizes test conditions for each test item in scope. Test conditions address the test objectives, must be traceable to the test basis, and take product risks into account. In incremental or iterative models, this includes scoping regression testing based on impact analysis; in Agile, test conditions can be expressed as acceptance criteria reflecting user story risk.

The TA can proceed in stages: starting with high-level conditions such as “functionality of screen x,” then more detailed ones such as “screen x rejects account numbers that are one digit too short.” This supports sufficient coverage and lets test design start early, even for user stories still being refined. The TA involves stakeholders in reviewing test conditions to confirm the test basis is understood and testing stays aligned with objectives.

1.2.2 Test Design K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic, and can summarize, compare, classify, and give examples for the concept.

Test design describes how to perform testing to achieve the stated test objectives, typically via test cases. How it is performed depends on required coverage, the test basis, the SDLC, project constraints, and tester knowledge and experience.

The TA determines where low-level or high-level test cases are appropriate, and in both cases must identify clear pass/fail criteria. Test cases are designed for new or changed test conditions according to the quality criteria; for regression, selecting existing high-level test cases or adapting existing low-level ones based on prioritization is usually sufficient.

The TA captures traceability between the test basis, test conditions, and test cases. In experience-based testing, test cases are not always documented — test conditions may instead guide execution. The TA can also design some test cases directly from high-level test objectives.

The TA also defines test environment requirements and identifies, creates, and specifies test data requirements during this activity. Exit criteria from test planning — and other signals such as residual risk levels or project constraints like budget or time — determine when enough test cases have been designed.

Test design can be tool-supported but should stay tool- and technology-agnostic. It applies a systematic approach using test techniques, or is done ad hoc otherwise.

Key distinction

Test cases have a communicative role: they should be understandable not only by the tester who executes them, but by other testers (who may not be the author), by developers who may implement or rerun tests after a failure, and by auditors who may need to approve them.

1.2.3 Test Implementation K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic, and can summarize, compare, classify, and give examples for the concept.

During test implementation, the TA provides the testware needed for test execution, organizing test procedures and test scripts into test suites or suggesting test cases for automation. Defining test procedures requires identifying constraints and dependencies that influence execution order. Beyond the steps in test cases, test procedures include steps for setting up initial preconditions (e.g., loading test data from a repository), verifying expected results and postconditions, and resetting after execution (e.g., resetting database, environment, and system).

The TA prioritizes test procedures and scripts for execution based on prioritization criteria from risk analysis and test planning, and identifies which should run on the current version of the test object — enabling related tests (new features, regression) to run together in a specific test run. The TA updates traceability between the test basis and other testware, and can assist the test manager in defining a test execution schedule, including resource allocation.

The TA creates input and environment data to load into databases and other repositories; this data must be “fit for purpose” for the specific test objectives. The TA also verifies the test environment is fully set up and ready — best done by designing and running a smoke test. The test environment should reveal defects in the test object through execution, operate normally absent failures, and, if required, adequately replicate the production or end-user environment.

The level of detail and complexity of test implementation work can be influenced by how detailed the test conditions and test cases are. Where regulatory rules apply, testware should provide evidence of compliance with applicable standards.

1.2.4 Test Execution K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic, and can summarize, compare, classify, and give examples for the concept.

Test execution is carried out according to the test execution schedule. Typical TA tasks are executing tests, comparing actual results to expected results, analyzing anomalies, reporting defects, and logging test results.

The TA executes tests manually — including exploratory testing, executing test procedures, regression testing, and confirmation testing. For exploratory testing, the TA can use session-based testing with test charters. The TA can also run automated test scripts, though running them and analyzing failures may instead be the task of developers, test automation engineers (TAEs), or technical test analysts (TTAs).

The TA analyzes anomalies from manual or automated execution to establish likely causes. An anomaly may reflect a defect in the test object, but could also stem from missing preconditions, incorrect test data, defects in test scripts or the environment, or misunderstood specifications. The TA logs actual results, communicates defects based on observed failures, and reports on them if needed. The TA updates traceability between the test basis and other testware based on results, which enables transforming results into high-level risk or coverage information for stakeholder decisions.

Beyond these typical tasks, the TA evaluates test results by:

Recognizing defect clusters that may indicate a need for more testing in a particular part of the test object.

Manually re-executing failed automated tests to rule out a false-positive result from test automation.

Suggesting additional tests based on what was learned during previous tests.

Identifying new risks from information obtained during test execution.

Suggesting improvements to test design or implementation, or to the system under test.

Suggesting improvements to regression test suites, including refactoring, scope adjustments, and automation.

1.3.1 High-Level Test Cases and Low-Level Test Cases K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic, and can summarize, compare, classify, and give examples for the concept.

A high-level test case (also called an abstract or logical test case) describes the circumstances in which the test object is examined by indicating which test conditions it covers. High-level test cases are suitable for ensuring tests cover all relevant test conditions; they contain no concrete preconditions, input data, expected outputs, or postconditions — all expressed at an abstract level.

A low-level test case (also called a concrete or physical test case) is the detailed refinement of a high-level test case: what data needs preparing, what actions the tester must take, and what the concrete expected result is. It contains specific preconditions, input data, expected results, and postconditions.

High-level test case

Abstract; states which test conditions are covered without concrete detail. Example: “order more than one book, with the order price resulting in a discount; expected result: discount is assigned.”

Low-level test case

Concrete refinement with specific data and results. Example: “order books B1 ($10) and B2 ($20), total order price $30; expected result: 10% discount assigned, total price $27.”

Typically the TA designs high-level test cases first, as the foundation for low-level test cases; one high-level test case can be implemented as one or more low-level test cases. Sometimes a test case remains high-level, with the TA determining concrete information during execution — for instance, guiding test objectives within a test charter for session-based testing, elaborated during execution.

The transition from high-level to low-level is more than filling in concrete values — it is a step from conceptual to technical, often deferred from test design to test implementation, especially where specific test data is needed. The TA must ensure everything necessary to execute the low-level test case is known. In practice, many test cases are hybrid: concrete in some aspects, abstract in others, reflecting a trade-off between maintainability and comprehensibility.

1.3.2 Quality Criteria for Test Cases K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic, and can summarize, compare, classify, and give examples for the concept.

Neglecting test case quality can lead to high maintenance costs, reduced comprehensibility, or execution delays. The following quality criteria are a first step towards more maintainable test cases.

Correctness

A test case must facilitate accurate verification of the test conditions it is based on.

Feasibility

It must be possible to execute the test case.

Necessity

Every test case should cover a clear objective stated in its title or summary; avoid duplicates and don’t design test cases for things that should not be tested.

Understandability

Others besides the author may review, modify, and execute the test case, so it should be written in a language and format understandable to all stakeholders, without explaining the obvious; complex test cases should be simplified or split.

Traceability

Test cases should trace to test conditions, requirements, and risks so the TA can keep them up to date.

Consistency

Consistent language, formatting, and structure ease understanding and maintenance; the TA may use a glossary.

Precision

There should be only one interpretation of a test case, avoiding ambiguous terms like “suitable,” “as needed,” or “several” that could cause false-negative or false-positive results.

Completeness

All necessary attributes should be present, including required test data and a clear expected result, to avoid doubt when comparing with the actual result.

Conciseness

Granularity should match the test basis and test conditions; smaller, focused test cases ease finding failure causes, combine flexibly into procedures and suites, and don’t block other tests when they fail.

The format and level of detail of test cases depend on the project and product context and should be agreed within the test team.

The test environment is a critical success factor for manual and automated execution alike, impacting testability, defect detection, overall testing costs, and result reliability. A test case that passes or fails in the test environment should produce the same result in production. Ideally, the environment is robust, predictable, and integrated with the test automation framework where required.

The TA may define test environment requirements during test design, based on analysis of: test conditions, test cases, and test data requirements; test levels and test types, which influence the trade-off between environment flexibility and similarity to production; and the availability and independence of components and systems, which may indicate a need for test doubles such as stubs or drivers.

1.3.4 Determining Test Oracles K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic, and can summarize, compare, classify, and give examples for the concept.

A test oracle is needed to determine expected results in dynamic testing. Ideally the test basis provides it (e.g., a textual or formal specification); human experience or knowledge of the test object can also serve as an oracle. An automated oracle may be needed for cost-effectiveness, e.g., when inputs are automatically generated or human oracles are costly.

Depending on the quality and completeness of the test basis or system characteristics, a cost-effective oracle may not be available — this is the test oracle problem. Typical contributing factors include data-related complexity, non-determinism (e.g., AI-based systems), probabilistic behavior, and missing or ambiguous requirements.

Pseudo-oracles

Independently developed systems fulfilling the same specification as the test object (e.g., legacy systems, simplified versions). Expensive to develop for complex objects but typical for critical systems.

Model-based testing

Formalizes the test oracle as part of the test model, enabling generation of expected outputs and derivation of tests from the model; behavior-based techniques often implement an automated oracle.

Property-based testing

Uses specified properties of the test object to verify relations between input and expected result; a test fails if the relation is not met. Well suited to automation, but effectiveness depends on relations that may be hard to determine.

Metamorphic testing

A technique for addressing the test oracle problem, covered in detail in Chapter 3.

Human oracles

Use human capability to determine expected results. Costly and scarce, but preferred in some approaches such as exploratory testing.

Assertions

Executable statements built into test automation code or the test object itself to verify state or behavior; when built into the test object, they usually verify only what is necessary for the task to continue.

During test design, the TA identifies and requests test data that may need preparation or provisioning for execution, considering purpose, format, and context of use.

Similarity with production data

Production data reflects real-world data but may lack variability; synthetic data allows controlled variability and should reflect production patterns, distributions, and outliers, though it may miss defects that only occur with real data. Personas help create realistic, user-centered data for diverse scenarios.

Confidentiality

Sensitive data (e.g., personal information) needs protection. Pseudonymized data replaces personal information with artificial identifiers; anonymized data removes identifiable information. The TA must observe applicable regulations such as GDPR (EU) or HIPAA (U.S.).

Purpose

Test data determines preconditions and expected results affecting system state and configuration (e.g., system time and date), and specifies user permissions and relations between products, departments, and categories.

Coverage criteria

Test data must align with the coverage criteria of the chosen technique, including invalid data for negative tests.

Data format

Systematic data management, e.g., in API testing, may require structured data such as CSV, JSON, XML, or database formats.

Traceability

Traceability keeps test data maintainable as changes are made to test cases.

Maintainability

Hard-coded test data in low-level test cases should be avoided; test logic should be separated from test data to ease defect detection and maintenance.

Dependencies

Dependent data requires a series of steps to create.

Availability

Service virtualization can address missing data by simulating absent or inaccessible services to interact with external systems.

Time sensitivity and data aging

Test cases involving outdated or time-sensitive data may cause unexpected or inaccurate system behavior.

1.3.6 Developing Test Scripts Using Keyword-Driven Testing K3K3: ApplyThe candidate can carry out a procedure when confronted with a familiar task, or select the correct procedure and apply it to a given context.

In keyword-driven testing, the TA creates test scripts using keywords; implementing the test scripts is the task of the TTA, TAE, or a developer. The TA identifies and specifies keywords by analyzing the test basis or collaborating with stakeholders.

Keywords fall into two categories: action keywords, which interact with the test object (executing functions, submitting data, navigating), the test environment (setting up configurations, activating simulators), or other components (triggering an interface); and verification keywords, which assert whether the actual result matches the expected result.

Keywords reside on at least two abstraction layers. Domain layer keywords correspond to business-related actions and reflect application-domain terminology, abstracting away technical interface details. Test interface layer keywords communicate with the test object, environment items, or other systems via their test interface and reside on the lowest abstraction layer. Additional intermediate layers may support keyword maintainability.

Keywords can be atomic or composed of other keywords; a keyword’s structure and its abstraction layer are independent attributes, though composite keywords often sit at a higher abstraction level while atomic keywords tend toward the test interface layer.

The TA’s tasks in keyword-driven testing include:

Specifying keywords and their parameters.

Specifying keyword test cases — test scripts using keywords.

Specifying additional steps such as preconditions, verification actions, and environment cleanup after the test.

Maintaining keyword test cases to reflect changes to the test object.

Executing keyword test scripts, automated or manual.

Analyzing failed keyword test cases to determine the cause of failure.

Example

User story: “As a member, I want to authenticate myself, such that I get access to the facilities,” with acceptance criterion “valid member cards can be used for authentication.” The TA may specify an action keyword Authenticate Member with a parameter member card, and a verification keyword Verify Access. The TA then checks whether the identified keywords sit at the appropriate abstraction layer.

When specifying keywords, the TA must keep in mind that keywords must:

Contain a verb (plus noun).

Use the imperative form of the verb (plus noun).

Be unique in their meaning.

Be adequately documented.

Reflect the vocabulary of the application domain.

Be reusable.

When composing keyword test cases, the TA may spot missing keywords and specify them immediately. Keyword test cases may be written in various formats, such as lists or tables. Keywords may change over a project’s lifetime and are prone to redundant specification — these recommendations aim to avoid redundancy and reduce maintenance effort. Although keyword-driven testing is a test automation approach, manual testing can benefit from it too, and doing so supports a later transition from manual to automated testing.

The Tasks of the Test Analyst in Risk-Based Testing

Risk-based testing prioritizes test effort by the risk level of each test item, an approach the test manager sets and the test analyst (TA) actively helps implement. It rests on two pillars — risk analysis and risk control — and because risk levels shift over time, it also depends on regular risk monitoring throughout the lifecycle.

  • impact analysisThe identification of all work products affected by a change, including an estimate of the resources needed to accomplish the change.
  • product riskA risk that impacts the quality of a product.
  • regression testingA type of change-related testing to detect whether defects have been introduced or uncovered in unchanged areas of the software.
  • risk analysisThe overall process of risk identification and risk assessment.
  • risk assessmentThe process to examine identified risks and determine the risk level.
  • risk controlThe overall process of risk mitigation and risk monitoring.
  • risk identificationThe process of finding, recognizing and describing risks.
  • risk mitigationThe process through which decisions are reached and protective measures are implemented for reducing or maintaining risks to specified levels.
  • risk monitoringThe activity that checks and reports the status of known risks to stakeholders.
  • risk-based testingA test approach in which the management, selection, prioritization, and use of test activities and resources are based on corresponding risk types and risk levels.

Risk analysis covers risk identification and risk assessment. The TA often holds unique knowledge of the system, plus experience and intuition about what usually goes wrong, what impact it has, and how testing can mitigate it — which makes the TA a valuable stakeholder in product risk analysis.

2.1.1 Risk Identification

In risk identification, the TA contributes their own experience and knowledge to a range of activities, and can also interview stakeholders directly to learn what they consider the most significant risks from their perspective.

Retrospectives

The TA draws on lessons from past iterations or projects to surface risks likely to recur.

Risk workshops

Structured sessions where the TA and other stakeholders jointly surface and discuss product risks.

Brainstorming

Checklists

The TA helps create checklists that capture recurring risk categories for systematic identification.

Stakeholder interviews

The TA talks directly to stakeholders to understand what they view as the most significant risks.

During risk assessment, the TA works with other stakeholders to determine the level of each risk by estimating several factors:

Potential damageFinancial, environmental, and reputational damage that could result.

As the final part of product risk assessment, the TA proposes suitable test activities — static and dynamic — to mitigate each identified product risk. Depending on the risk level, the affected test item type, and the quality characteristic involved, the TA indicates the required test levels, test types, test techniques, levels of independence of testing, and test thoroughness.

Key distinction

In the spirit of shift left, the TA identifies which test activities can mitigate a given risk earliest, since catching a risk sooner generally minimizes total testing effort.

2.2.2 Regression Testing and Test Selection

The main objective of regression testing is to build confidence in the quality of the test object after a change. But executing every regression test is often impossible due to constraints on time, budget, test environment, or test data. This mainly affects manually executed tests, but it also applies to automated tests — for example, when test cycles are short and many automated tests are long-running. As a result, the TA must select appropriate regression tests, and the scope of regression testing should be reviewed with every test cycle; that review may conclude the existing regression test suite needs adjusting.

Note

The most reliable technique for selecting automated regression tests is impact analysis, supported by tools built on an automated configuration management system. These tools register which configuration items are exercised by each test case; when a change occurs, they track which items were modified and select the tests that interact with those items — focusing execution on the areas most likely to reveal failures.

For manual test execution, no single technique has proven consistently superior — results depend on the situation, so the TA chooses based on context. Commonly used techniques include:

Risk-based test selection

The TA keeps the regression suite traceable to the risk register; when a change updates the register, the TA adjusts the suite to cover the highest risk levels.

History-based testing

The TA re-runs tests that previously exposed defects or were sensitive to similar changes, and periodically includes long-unrun tests to confirm they still pass.

Coverage-based testing

The TA selects a small number of tests that achieve as much coverage as possible for the chosen technique(s), balancing test count against coverage gained.

Requirement traceability matrix

Used to assess how requirement changes affect associated tests, including indirect impacts on other features; in Agile, the TA selects tests covering the acceptance criteria affected by changed user stories.

Testing based on operational profiles

The TA selects tests reflecting real usage patterns (e.g. login, search, add to cart, place order for an online store); when changes are large, this quickly checks overall functionality, and the TA prioritizes the most frequent, business-critical patterns if too many tests result.

Impact analysis (manual)

The same technique used for automated selection can also guide manual test selection when the TA knows which manual tests interact with the changed configuration items.

Watch out

A single technique is often not enough — a combination gives a more comprehensive and effective regression suite. But the TA must balance the need for coverage against keeping the suite a manageable size. After each test cycle, the TA analyzes the results to judge how effective the applied techniques were (see section 5.3.1), then retains effective techniques and replaces ineffective ones next time — a continuous improvement loop that matters most in iterative and incremental development, where changes are frequent.

3.1

Data-Based Test Techniques

Here, domain means the set of input data of a test item. Input from different areas of the domain triggers different behaviors, and data-based test techniques aim to verify the implementation handles specific domain areas correctly. Foundation Level already covers two data-based techniques — equivalence partitioning (EP) and boundary value analysis (BVA). This chapter adds three more: domain testing (which extends EP and BVA to domains with multiple parameters and complex partitions), combinatorial testing (which focuses on interactions between multiple parameters in a multidimensional domain), and random testing (which selects random inputs based on a specified probability distribution).

3.1.1 Domain Testing K3K3: ApplyThe candidate can carry out a procedure when confronted with a familiar task, or select the correct procedure and apply it to a given context.

Domain testing verifies whether the test item behaves as specified on a domain's equivalence partitions and at their borders. An equivalence partition here is defined by an expression that combines atomic conditions with Boolean operators (AND, OR, NOT) and may involve several interacting variables. Each atomic condition defines a border of the partition. A closed border uses the operators ≤, ≥, or =; an open border uses <, >, or ≠.

Example

The expression “height > 1.29 meters AND weight / height² ≥ 30” defines an equivalence partition of a two-dimensional domain over two variables. It has two borders: an open one (height > 1.29) and a closed one (weight / height² ≥ 30).

Domain testing seeks to detect defects in how an equivalence partition was implemented — a wrong operator or a wrong constant — by choosing coverage items that can reveal such defects. Coverage criteria are expressed using four point types relative to a given border:

ON point

For a closed border, a point that lies exactly on the border. For an open border, a point just inside the partition, as close to the border as the given precision allows.

OFF point

For a closed border, a point just outside the partition, as close to the border as precision allows. For an open border, a point that lies exactly on the border.

IN point

A point that belongs to the equivalence partition and is not itself an ON point.

OUT point

A point that lies outside the equivalence partition and is not itself an OFF point.

Key distinction

Each point type is relative to one particular border — the same coordinate can be an ON point for one border and an IN or OUT point for another border of the same partition.

Two coverage criteria build on these point types:

Coverage criterionRequired coverage items
Simplified domain coverageFor each border defined by <, ≤, >, or ≥: one ON and one OFF point. For a border defined by =: one ON point and two OFF points on different sides of the border. For a border defined by ≠: one OFF point and two ON points on different sides of the border. Each OFF point must be as close as possible to its corresponding ON point, given the precision in use.
Reliable domain coverageFor each border defined by <, ≤, >, or ≥: one ON, one OFF, one IN, and one OUT point. For a border defined by =: one ON point and two OFF points on different sides. For a border defined by ≠: one OFF point and two ON points on different sides.

For both criteria, the number of coverage items grows linearly with the number of borders — but it can be optimized by reusing the same coverage item for different borders. Reliable domain coverage needs somewhat more coverage items than simplified domain coverage, but it can detect considerably more domain defects.

Domain testing can be applied at any test level, and it generalizes EP and BVA to more complex, multi-variable domains.

3.1.2 Combinatorial Testing K3K3: ApplyThe candidate can carry out a procedure when confronted with a familiar task, or select the correct procedure and apply it to a given context.

Some failures only occur for specific combinations of parameter values — interaction failures. Combinatorial testing aims to reveal these by systematically exploring parameter value combinations. Test conditions typically combine either configuration parameters (each combination tested with the same test case) or input data values (each combination becoming part of a distinct test case). A parameter-value pair is a parameter together with one of its values, e.g. ‘(color, red)’.

Base choice coverage

Assumes some parameter-value pairs matter more than others. A base value is chosen for each parameter, forming a base coverage item. Further coverage items are created from the base item by swapping in each non-base value for one parameter at a time.

Pairwise coverage

Coverage items are pairs of parameter-value pairs for any two parameters. Tools exist to generate coverage items, though finding the minimal test set that achieves pairwise coverage is generally a hard problem.

When a parameter has many values, EP can first reduce the number of values considered, shrinking the resulting combination set. A classification tree or a feature model helps capture parameters and their values for this purpose. The final test case count can also be shaped by constraints between parameter-value pairs, combinations known to be problematic that are added manually, or combinations that are invalid or infeasible.

Note

Not every parameter contributes to a given failure — most failures are triggered by a single parameter value or by interactions among a small number of parameters. This matches the coupling effect hypothesis: detecting simple defects tends to also uncover complex ones. One limited study found about 97% of failures were caused by only one or two interacting conditions — evidence that pairwise testing is an effective technique.

Tools are available to support combinatorial testing generally.

3.1.3 Random Testing K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic, and can summarize, compare, classify, and give examples for the concept.

Random testing selects test data randomly from the input domain according to a specified probability distribution. For validation, a distribution based on operational profiles is recommended; for verification, the distribution should stay usage-agnostic to avoid bias. Expected results are usually added via a test oracle, which most often needs to be automated. Random testing can be unguided (a fixed distribution throughout) or guided — as in adaptive random testing — where the distribution evolves based on previously selected values, aiming to cover the domain effectively since defects often cluster in specific regions. Random testing has no recognized coverage criteria, so exit criteria can only rely on measures like number of tests executed or testing time.

Benefits

Valuable when domain knowledge is limited or large volumes of test data are needed; cost-effective; gives probabilistic insight into reliability; helps avoid biases such as misplaced trust in some code leading a manual tester to overlook defects there.

Limitations

Neglects data semantics, which can miss defects tied to data meaning; can overlook certain defects and generate redundant tests; depends on an automated test oracle; random outputs can lead to inconsistent test results across runs.

Random testing is traditionally seen as less effective than other techniques, but recent empirical studies show that, under the right circumstances, it can be more effective and efficient than other data-based techniques. It underlies fuzz testing and chaos engineering.

3.2

Behavior-Based Test Techniques

Behavior-based test techniques derive test cases from specifications of the dynamic, state-dependent behavior of the test item. This chapter covers three: CRUD testing, state transition testing, and scenario-based testing. CRUD testing and scenario-based testing extend the Foundation Level black-box toolkit; state transition testing gets extra coverage criteria on top of what Foundation Level already teaches.

3.2.1 CRUD Testing K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic, and can summarize, compare, classify, and give examples for the concept.

CRUD testing verifies the lifecycle of data entities processed by the test item. CRUD stands for the four basic operations a function can perform on an entity: create, read, update, delete. A CRUD matrix gives an overview of entity lifecycles — its columns are entities, its rows are functions, and each cell records which operations (C, R, U, D) that function performs on that entity. Building it means the TA determines, for every function, which of the four operations it performs on which entities; the read operation deserves special attention since it's often implicitly tied to the C-U-D operations.

Completeness testing

Static testing that verifies all four operations occur for every entity — that its whole lifecycle has been implemented. A missing operation is an anomaly requiring investigation.

Consistency testing

Dynamic testing that integrates the various functions and checks an entity is used consistently — that functions interact correctly when handling it. Test cases combine functions per entity to cover its full lifecycle, and should include negative cases (e.g. reading an entity never created).

CRUD coverage is the number of operations executed by the test suite divided by the total number of operations in the CRUD matrix. A more rigorous variant treats specific operation combinations as coverage items — for example, requiring that after each U, all possible Rs are covered.

CRUD testing is used primarily at the system level, targeting defects in how the test item treats entities: data integrity violations, access control defects, and data inconsistencies.

3.2.2 State Transition Testing K3K3: ApplyThe candidate can carry out a procedure when confronted with a familiar task, or select the correct procedure and apply it to a given context.

Many complex systems are stateful — their reaction to an event depends on the system's current state. Embedded systems, dialog-based systems, control systems, and systems managing entity lifecycles are typical examples. A state simplifies internal complexity so stakeholders can more easily understand expected behavior. During test analysis, the TA must ensure a state-based model represents the expected behavior at the level of detail testing needs; if the test basis already has such a model, the TA checks it contains the required test conditions and adapts or replaces it if not.

In state-based models, nodes represent states and edges represent transitions, which are triggered by events and may carry guard conditions and actions. Variants in use include extended finite state machines, Harel state charts, and UML state machines.

Beyond the state transition coverage criteria from Foundation Level, two further criteria have strong empirically-proven defect detection effectiveness:

0-switchSingle transitionEquivalent to valid transitions coverage; a sequence of just 1 transition. Used frequently in practice.
1-switchTransition pairA pair of incoming and outgoing transitions at one state (2 consecutive transitions). Also used frequently in practice.
2-switch and higherLonger sequencesN+1 consecutive transitions. Only indicated when there's high risk of failure from unexpected event sequences, since the number of N-switches can grow exponentially with N.

N-switch coverage applies to valid sequences of N+1 consecutive transitions (an “N-switch”); extending an N-switch at its end by one more valid transition yields an N+1 switch. Round-trip coverage applies to loops in the state-based model — a round trip is a loop whose start and end states are the same, with no other state in the loop repeated. The coverage items are the round trips themselves, and this criterion has been found highly effective at detecting defects.

State transition testing suits automation via model-based testing tools well. Like most black-box techniques, it contributes to defect prevention by surfacing specification defects during modeling itself. It can be applied at any test level.

3.2.3 Scenario-Based Testing K3K3: ApplyThe candidate can carry out a procedure when confronted with a familiar task, or select the correct procedure and apply it to a given context.

Scenario-based testing evaluates the test item's behavior in realistic scenarios. User research, user stories, personas, and user journey maps can all help identify valuable scenarios. The TA builds a scenario model from sequences of actions that form workflows through the test item — this chapter discusses two model types (others exist, e.g. flowcharts, BPMN diagrams, sequence diagrams, or collaboration diagrams, but aren't covered further):

Activity diagram

A graphical representation of workflow within a system, particularly useful for business processes but also usable for control flow. It extends flowchart notation to allow modeling concurrency, using start/end nodes, actions, transitions, decision nodes, merge nodes, fork nodes, join nodes, and swim lanes.

Use case

A textual or graphical description of the interactions between a user and a system, or between systems, expressed as scenarios of action sequences.

A use case distinguishes three scenario types:

Main scenario

The “happy path” — the typical, expected sequence of actions that achieves the goal from the user's perspective. A use case can have only one main scenario.

Extension (alternative)

A sequence of actions, different from the main scenario, that still eventually achieves the main scenario's goal.

Exception

A sequence of actions that fails to achieve the main scenario's goal, due to an unexpected action such as abnormal use or invalid input.

The TA designs test cases to cover scenarios — the coverage items — usually with risk-based prioritization. When the scenario model has no loops, each scenario can get its own test case. Where loops exist, the number of potential paths can be infinite, so simple loop coverage applies instead.

1Zero iterationsThe loop is skipped entirely.
→
2One iterationThe loop body executes exactly once.
→
3Typical iterationsThe loop body executes more than once, a typical number of times.

4Maximum iterationsThe loop body executes the maximum possible number of times, if feasible.

Scenario-based coverage is the number of executed scenarios divided by the number of all identified scenarios.

Scenario-based testing is common in system testing and acceptance testing, often as end-to-end testing of functional suitability from the user's perspective. It also applies at other test levels and in non-functional testing, where scenarios can form the operational profiles used to guide testing.

3.3

Rule-Based Test Techniques

Rule-based test techniques verify the implementation of a test item's stateless behavior — behavior specified by rules that hold regardless of state, such as business rules. This chapter covers two: decision table testing and metamorphic testing.

3.3.1 Decision Table Testing K3K3: ApplyThe candidate can carry out a procedure when confronted with a familiar task, or select the correct procedure and apply it to a given context.

Foundation Level covers the basics of decision table testing; here the TA goes further. Work usually starts either by building a full decision table or by analyzing one already in the test basis. A full table's number of rules is the product of the numbers of values of its conditions — a count that grows exponentially with the number of conditions and values, which is why minimization matters. Minimization starts from an original table (full or not) and derives an equivalent table with fewer rules.

Tables are minimized by merging rules with the don't care operator, ‘–’. Infeasible rules — combinations of condition values that can never occur — should be disregarded when merging, and are often removed before merging begins. One systematic minimization algorithm looks for action-equivalent rules that differ in only one condition but together cover all of that condition's possible values; these get merged, with the differing value replaced by ‘–’. The result can depend on the order columns are minimized in, so it doesn't always reach an optimal solution — the TA must check whether further minimization is still possible.

The TA reviews the resulting table, ideally with other stakeholders, against four criteria:

Consistency

If two different rules apply to the same combination of condition values, they must be action-equivalent.

Feasibility

The table contains no infeasible rules.

Completeness

No feasible combination of condition values is missing.

Correctness

The rules correctly model the system's intended behavior.

Watch out

It's also advisable that rules don't overlap — that at most one rule applies to any given combination of condition values. Overlaps can creep in when the original table was already minimized, or when rules were merged incorrectly.

The checksum procedure uses the rule count of a minimized table to flag overlaps and gaps. For each rule in the minimized table, calculate how many rules of the original table it represents: a rule with no ‘–’ anywhere (individual values for every condition) scores 1, and each ‘–’ multiplies that rule's score by the number of individual values the respective condition can take. Summing every rule's score gives the minimized table's checksum.

Checksum comparisonWhat it indicates
Minimized checksum < original checksumThe minimized table is incomplete.
Minimized checksum > original checksumSome rules overlap, or extra rules exist — e.g. infeasible condition combinations.
Minimized checksum = original checksumConsistent with correct minimization — but equal checksums alone do not prove the two tables are equivalent.

Decision table coverage is the number of columns exercised divided by the total number of feasible columns. When turning a rule into a test case, the TA must implement its conditions and actions and decide how to handle any ‘–’ condition value, since it represents at least two possible values. If the table's associated risk level is high, the TA should skip minimization altogether and instead measure coverage of the feasible columns in the full decision table.

3.3.2 Metamorphic Testing K3K3: ApplyThe candidate can carry out a procedure when confronted with a familiar task, or select the correct procedure and apply it to a given context.

Metamorphic testing (MT) generates test cases from an existing source test case. One or more follow-up test cases are produced by “metamorphizing” the source's inputs according to a metamorphic relation (MR) — a property of the test item describing how a change to the inputs should be reflected in the expected results. The TA combines source and follow-up test cases into one test procedure with a joint result evaluation: if the MR holds, the test passes; if not, it fails, and subsequent debugging must determine which individual test case actually failed.

Example

Consider a function that averages a series of numbers. A source test case supplies a series and an expected average, and passes when run. One MR states that permuting the series doesn't change the average — letting the TA generate follow-up test cases that reorder the same numbers while keeping the same expected result. A different MR for the same function states that multiplying every number in the series by x multiplies the expected average by x too — letting the TA generate any number of follow-ups just by varying x.

MT is also valuable in the presence of a test oracle problem, where the expected results of the source and follow-up test cases simply aren't available, so their individual results can't be checked directly — only the relation between them can be. For example, an AI-based actuarial program predicting age at death might use the MR that increasing the number of cigarettes smoked should decrease the predicted age of death.

There are currently no recognized coverage measures for MT that give useful exit criteria — covering each MR just once only partially verifies expected results. The TA can combine MT with random testing, generating many low-level source and follow-up test cases for the same MR.

MT applies to most test items, in both functional and non-functional testing. It is a preferred technique for AI-based systems.

3.4

Experience-Based Testing

The TA also draws on experience-based testing — expertise and past encounters used to guide testing. This section covers the TA's use of documentation in session-based testing and checklist-based testing, plus crowd testing. All experience-based techniques can be applied within collaboration-based testing, such as acceptance test-driven development.

3.4.1 Test Charters for Session-Based Testing K3K3: ApplyThe candidate can carry out a procedure when confronted with a familiar task, or select the correct procedure and apply it to a given context.

In exploratory testing, a test charter gives a test session its mission — scope and objectives, plus information such as limitations, timelines, and risks. It's a roadmap that structures the session while still letting the TA explore the system flexibly when needed. Crucially, a test charter does not specify the exact test suites to be executed in the session.

Designing a test charter means weighing three groups of influencing factors:

Customer and requirement factors

Requirements elicited from clients, business use cases for the system, quality requirements, and user journey maps.

Product factors

Functional flows, the product's principal goals, product features, software design, and interfaces.

Project management factors

Time constraints, project purpose, estimated effort, and business value.

A test charter's core is a mission that states the test objective, in a popular lightweight format:

Format

“Explore [target] With [resources] To discover [information]” — where [target] is what's explored, [resources] is what the TA will use, and [information] is the kind of insight sought.

Beyond the mission, a test charter may include further information, such as:

How much detail a charter includes trades off against the TA's flexibility: stating only general objectives leaves room to explore, while specifying test techniques constrains that exploration.

3.4.2 Checklists for Experience-Based Testing K3K3: ApplyThe candidate can carry out a procedure when confronted with a familiar task, or select the correct procedure and apply it to a given context.

Checklist-based testing is widely used for its adaptability, simplicity, and effectiveness. Checklists ensure the TA covers all known essential aspects of a test item, preventing overlooked areas, and they introduce consistency across test cycles and across different TAs. They record the TA's past experience with failures and defects.

Preparing checklists is typically the TA's job. Building one that's reusable, maintainable, clear, and efficient takes real effort, and follows roughly three steps:

  1. 1

    Determine scope, objectives, and format

    These choices drive testing depth and required detail. A read-do checklist lists the major elements to consider for a process (e.g. concrete invalid inputs to check for a field). A do-confirm checklist instead guides the thought process with exploration ideas (e.g. checking whether search results are relevant).

  2. 2

    Collect information for checklist items

    Gather insight from experienced professionals, browse defect libraries and taxonomies, review relevant documentation, and analyze risks, test cases, and potential scenarios. Items should be clear, specific, unambiguous, consistent, relevant, maintainable, actionable, and measurable — phrased as yes/no/not-applicable questions, and prioritized by importance, potential impact, and risk. Checklists are not comprehensive how-to guides; they're quick, simple tools for expert professionals.

  3. 3

    Structure and organize the checklist

    Group items into logical categories — by functional area, user role, test level, or another relevant criterion. Separate categories are especially useful for a long checklist. Reuse existing templates or predefined checklists aligned with industry standards where possible.

Note

A checklist is never finished. The TA continually reviews and refines it to reflect new findings, changed priorities, tester feedback, or lessons from previous cycles — and sharing it with other testers promotes consistency and collaboration, and helps them understand the test items and where to focus.

3.4.3 Crowd Testing K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic, and can summarize, compare, classify, and give examples for the concept.

Crowd testing distributes tests among a group of internal or external testers with diverse backgrounds and locations. It can be a cost-effective way to validate usability, covering both functional and non-functional quality characteristics. It does not replace TAs applying test techniques — but it can increase coverage of diverse test environments.

Diverse test environments

Testers in various geographical locations, using a wide variety of devices, browsers, network conditions, and configurations.

Flexibility

Easily scalable to handle many tests in a short time.

Cost-effectiveness

Typically cheaper than maintaining a large, diverse in-house test team or supplementing with external testing services.

Rapid feedback

Testers can respond quickly, helping identify and fix failures early.

Real user perspective

Testers can be actual application users, giving strong insight into user experience and usability — especially valuable in user acceptance testing.

Variability

A wide variety of testers each run means results are less repeatable — a limitation, but one that also widens coverage and raises the chance of finding defects.

Unreliable quality of testing

Quality can vary significantly with individual testers' skills, though this may not matter when the goal is simply user experience feedback.

Communication challenges

Coordinating many testers across locations, time zones, cultures, and languages can be difficult.

Security

Sharing software with external testers raises data security and confidentiality risks — proper measures can mitigate this without disclosing sensitive details or enabling plagiarism.

Documentation and reporting

Comprehensive test documentation and managing a large volume of findings — including duplicates and false positives — is challenging with a large, diverse tester group.

Applying the Most Appropriate Test Techniques

Testing should be as effective and efficient as possible for its context. The TA supports the test manager in selecting the most appropriate test technique(s), and can also use automation to support test activities — including automating test design, covered below (test execution automation is covered in Chapter 1, section 1.3.6).

3.5.1 Selecting Techniques to Mitigate Product Risks K4K4: AnalyzeThe candidate can separate information related to a procedure or technique into its constituent parts for better understanding, and can distinguish between facts and inferences — typically to analyze a document, software, or project situation and propose appropriate actions.

Selecting the right test technique(s) is central to effective, efficient product risk mitigation, and depends on many factors:

Test objectives

Which aspects of the test object to evaluate, guided by the type of system under test.

Product risks

Most techniques focus on specific defect types — data-based techniques catch data handling, domain, UI, calculation, and parameter-combination defects; behavior-based techniques catch missing features, communication defects, and processing defects; rule-based techniques catch logic and control-flow defects.

Coverage-based exit criteria

Higher risk generally calls for more rigorous coverage — balanced against the trade-off between coverage strength and required effort.

Test basis

Model-based specifications point to model-based techniques; when a test oracle is hard to derive, techniques like metamorphic testing or experience-based testing can be used instead.

Recurring defect types

Known recurring defect types point to techniques that target them; a technique that worked before is often worth repeating.

Tester's knowledge and experience

Techniques the TA isn't familiar with shouldn't be used on critical assignments.

Software development lifecycle

Sequential models suit more formal techniques; iterative models suit lightweight techniques or automatable test design.

Customer and contract requirements

Contracts can mandate specific testing techniques.

Regulatory requirements

Standards can mandate specific testing techniques.

Project constraints

Time and budget constraints can rule out time-consuming techniques or ones needing expensive resources.

Defect prevention

4.1

Functional Testing K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic, and can summarize, compare, classify, and give examples for the concept.

Functional testing is one of the TA's core tasks. The ISO 25010 product quality model splits functional suitability into three sub-characteristics — functional completeness, functional correctness, and functional appropriateness. All three can be assessed by functional testing, but not every test activity addresses them equally well, so the TA must select the test levels and techniques that fit each sub-characteristic's product risks.

4.1.1 Functional Completeness Testing

Functional completeness testing should cover all specified tasks of the software and the intended users' objectives. The key question: is everything that is asked for implemented?

It should be addressed as early as possible — by reviewing the requirements specification in sequential development models, or by discussing user stories and their acceptance criteria during collaborative user story writing in Agile. In system testing, system integration testing, and acceptance testing, it can also be tested dynamically. Behavior-based techniques such as scenario-based testing fit well, though other black-box techniques are suitable too. Traceability between test basis, test conditions, and test cases is essential to determine the level of functional completeness achieved.

4.1.2 Functional Correctness Testing

Functional correctness testing answers whether actual results are correct — accurate, precise, and consistent — for valid and invalid inputs. Finding an effective test oracle that provides expected results in detail is crucial.

It can be tested at any test level, but in the spirit of shift left, most functional correctness testing should occur in component testing and component integration testing. Even where the TA is not responsible for these levels, the TA should still contribute to best achieve the test objectives. All black-box techniques, experience-based techniques, and collaboration-based testing are suitable.

4.1.3 Functional Appropriateness Testing

Functional appropriateness testing verifies that the functions facilitate accomplishing specified tasks and objectives. The focus is on whether everything implemented fulfills users' needs.

It may include user interface design reviews, especially for interactive applications. Dynamic testing starts with system testing and acceptance testing in sequential models, or with demo sessions in Agile. Exploratory testing and collaboration-based testing are most appropriate, and behavior-based black-box techniques are also suitable.

4.2

Usability Testing K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic, and can summarize, compare, classify, and give examples for the concept.

Usability refers to a broad concept of user-related quality characteristics, covering interaction capability from the ISO 25010 product quality model and beneficialness from the ISO 25019 quality-in-use model.

4.2.1 Aspects of Usability

Usability testing usually focuses on evaluating three aspects:

Interaction capability

Enabling users to complete tasks in specific contexts of use effectively, efficiently, and satisfactorily.

User experience

Addressing users' perceptions before, during, and after interacting with the test object.

Accessibility

Ensuring users with disabilities, diverse cultural backgrounds, or language barriers can use the system effectively and efficiently.

The TA can collaborate in usability testing from an early phase using their knowledge of the target user groups, their goals, their context of use, potential difficulties using the system, or negative user experience.

4.2.2 Usability Evaluation Techniques

The TA contributes to three principal usability evaluation techniques:

Usability reviews

Performed by usability experts to identify potential usability problems and deviations from established criteria, ranging from informal reviews to inspections. The TA adapts review criteria to the specific user groups, business objectives and priorities, and context of use — e.g. tailoring a generic usability checklist.

Usability test sessions

Future users or their representatives try to solve predefined tasks to evaluate whether tasks can be completed effectively, efficiently, and satisfactorily. The TA may help design scenarios for these sessions according to personas, user groups, or operational profiles.

User questionnaires or surveys

Including rating and feedback, these measure user satisfaction (e.g. SUMI and WAMMI). The TA can help design a questionnaire and evaluate responses against the specific goals of the targeted users within their context of use.

4.2.3 Accessibility Testing

A common test objective in accessibility testing is to verify compliance with standards.

Note

The international standard Web Content Accessibility Guidelines (WCAG) defines three levels of conformance — A, AA, and AAA — representing increasing degrees of web content accessibility. National standards include the United Kingdom's Equality Act and the United States' Americans with Disabilities Act. The TA identifies the required compliance level and the specific needs of the intended target group by analyzing the context of use.

4.4.1 Interoperability Testing K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic, and can summarize, compare, classify, and give examples for the concept.

The goal of interoperability testing is to verify that two or more components or systems can exchange information and mutually use the information that has been exchanged. When the exchange involves a data transformation, interoperability testing must include verification of that transformation.

Interoperability testing is particularly important when multiple systems need to collaborate, share data, or perform tasks together — especially in modern architectures such as cloud solutions, web services, microservices, containerization, and the Internet of Things. Interoperability usually happens across various architectural levels; the TA must understand the possible interactions to define proper test conditions. Not all interactions may be documented, so the TA may need to retrieve information indirectly from architecture and design documentation — understanding this documentation is crucial to ensure all important aspects of the interactions get tested.

Data transformation defects

Errors in transformations applied during the exchange of data.

Interpretation or use defects

Errors in how exchanged data is interpreted or used.

Communication defects

Errors in communication flows and protocols between systems.

Standards compliance defects

Failures to comply with relevant standards.

End-to-end functionality defects

Failures in functionality that spans the full interaction chain.

Design documentation defects

Errors or gaps discovered in the design documentation itself.

Interoperability testing is usually applied during integration testing. Suitable black-box techniques include data-based techniques focused on the exchanged data, behavior-based techniques for interpreting or using the data, and end-to-end functionality or rule-based techniques for data transformation. Experience-based techniques can usefully complement black-box testing.

Watch out

Test cases from functional testing or adaptability testing may be reused for interoperability testing — don't build a separate suite from scratch if existing cases already exercise the relevant interactions.

Software Defect Prevention

Defect prevention reduces the likelihood that defects (re)occur in work products and keeps defects from propagating to later phases of the SDLC — lowering cost and labor while raising productivity and product quality. It is a whole-team responsibility, and the test analyst (TA) contributes with domain knowledge, test expertise, and analytical skill: helping stop defects from being introduced, helping contain defects that do occur within the phase where they arose, and helping stop defects from recurring.

5.1

Defect Prevention Practices K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic, and can summarize, compare, classify, and give examples for the concept.

Defect prevention practices fall into three groups: preventing defect introduction (part of quality assurance activities), preventing defects from escaping to later SDLC phases (section 5.2), and preventing defects from recurring (section 5.3). Defect prevention is a whole-team responsibility, but the TA contributes using domain knowledge, test expertise, and analytical skills.

Participating in risk analysis

Ensures identified risks are properly mitigated — for example, by selecting the most adequate test techniques.

Reviewing requirements, models, and specifications

Allows early detection of defects in the test basis, preventing them from escaping into the code and significantly reducing the cost of fixing them.

Participating in retrospectives

Identifies potential improvements in test analysis, design, implementation, and execution — e.g. more effective techniques, targeting risk areas, or better test data and environments to reduce false-positive and false-negative results.

Defect data collection and evaluation

Collects detailed defect data to enable classification and statistical analysis, supporting root cause analysis and process improvement.

Participating in root cause analysis

Proposes corrective actions that address identified root causes, preventing defects from reoccurring.

The TA also assesses — usually together with the test manager — whether the measures taken have had the desired effect. Three metrics help evaluate that effectiveness:

MetricWhat it measures
Defect removal efficiency (DRE)The ratio of defects removed before release to the total number of defects (an unknown denominator, often estimated or replaced by defects found up to a set point after release, e.g. 6 months). A high DRE suggests fewer defects escape to production, implying better prevention practices — but it does not distinguish defects caught by prevention from those caught by detection.
Phase containment effectiveness (PCE)The number of defects introduced and removed within the same SDLC phase, relative to the total number of defects introduced in that phase. A high PCE means fewer defects escape to later phases.
Cost of qualityIllustrates the relationship between defect prevention, defect detection, and defect removal costs.

5.2

Supporting Phase Containment

Phase containment aims to detect and remove defects in the same SDLC phase in which they were introduced — in Agile, the shift left approach serves a similar purpose. This policy reduces the cost of quality. Because the test basis is a key input to test analysis and test design, the TA best contributes to phase containment by evaluating test basis quality: early attention here minimizes later effort and prevents defects from propagating forward. Two options let the TA find defects in the test basis: modeling for testing purposes, and reviewing the test basis with various review techniques.

5.2.1 Using Models to Detect Defects K3K3: ApplyThe candidate can carry out a procedure when confronted with a familiar task, or select the correct procedure and apply it to a given context.

Modeling provides abstractions of a system at a chosen level of precision and detail, helping stakeholders better understand the system being developed. It supports phase containment in three ways:

Detecting defects in specifications. Specifications are often informally written text. The TA can formally represent them using models, mapping and linking test conditions (e.g. requirements) to model elements for traceability. Formalizing and visualizing the test conditions efficiently reveals defects such as incompleteness, inconsistencies, or ambiguities. Modeling's strength is that it transforms the specification, whereas reviews check it in its original form — so modeling also helps the TA find appropriate solutions for the defects it detects. Example

Model-based testing (MBT) generates test cases and other test design testware from an MBT model and test selection criteria the TA defines. MBT is effective at finding specification anomalies because it allows comprehensive coverage and systematic exploration of expected behavior according to the model. Graphical MBT models also foster communication with stakeholders, building a shared understanding of the test basis.

5.2.2 Applying Review Techniques K3K3: ApplyThe candidate can carry out a procedure when confronted with a familiar task, or select the correct procedure and apply it to a given context.

A well-defined test basis is the cornerstone of work product quality and project success. Reviewing the test basis identifies and addresses defects early, preventing them from escaping to later phases. The TA can apply various review techniques during individual review; the best choice depends on reviewing goals, project objectives, available resources, test basis type, associated risks, business domain, and company culture.

Ad hoc reviewing

Carried out informally, without a structured process; reviewers get little or no guidance and document anomalies as they encounter them while reading. Needs little preparation but is highly dependent on reviewer skill, and left unmanaged can produce a high volume of duplicate anomaly reports from multiple reviewers.

Checklist-based reviewing

Evaluates the test basis against a predefined checklist, which reminds reviewers of specific points and de-personalizes the review. Checklists can be generic or specific to quality characteristics, test objectives, or test basis type; the TA tailors them to focus the review, keeps them updated with previously missed defects, and is not limited to the listed items.

Scenario-based reviewing

Simulates a process or activity to identify anomalies and refine the test basis. Most effective when the test basis is scenario-based (e.g. a use case or activity diagram), letting reviewers perform “dry runs” based on expected usage; reviewers are not limited to documented scenarios and should think beyond them.

Role-based reviewing

Assigns specific roles or responsibilities to reviewers, typically based on end-user types (experienced, inexperienced, senior, child) or organizational roles (administrator, regular user), each describable as a persona. Distributing responsibility by role gives comprehensive coverage while avoiding duplicated anomalies.

Perspective-based reading

Reviews the test basis from various viewpoints (designer, tester, marketer, administrator, end user), producing more in-depth individual review with less duplication among reviewers. Reviewers also attempt to generate the work product they would derive from the test basis — e.g. a tester drafting acceptance tests from requirements to check all needed information is present.

5.3

Mitigating the Recurrence of Defects

The TA can proactively help minimize defect recurrence in two ways: analyzing test results to improve test analysis and test design, and supporting root cause analysis with defect classification.

5.3.1 Analyzing Test Results to Improve Defect Detection K4K4: AnalyzeThe candidate can separate information related to a procedure or technique into its constituent parts for better understanding, and can distinguish between facts and inferences — typically to analyze a document, software, or project situation and propose appropriate actions.

Test results let the TA identify failures, and they also give feedback the TA can use to improve defect detection effectiveness.

Predicted vs. actual defect cluster analysis

Most defects usually cluster in a few components. After testing, the TA compares predicted defect clusters against actual ones; where more defects appear than expected, more rigorous testing may be applied there. Measurable criteria (e.g. defect density, defect severity) keep clusters clear and consistent — small clusters of critical or major defects usually matter more than larger clusters of minor or cosmetic ones.

Defect detection percentage (DDP) analysis

One of the most important test effectiveness measures for a test level; escaped defects counted should be limited to ones that level could have detected, with clear temporal limits and exclusion criteria for consistency. A low DDP signals ineffective defect detection, prompting the TA to analyze causes and propose improvements; DDP is best broken down by severity, since escaped-defect priority usually depends on it.

Structural coverage analysis

Assesses how thoroughly tests have exercised specific areas of the test object (e.g. statement, branch, or neuron coverage, usually tool-measured). Identifying low-coverage areas lets the TA target additional test effort there to discover previously escaped defects, weighing risk level when choosing where to add coverage.

Test gap analysis

Assesses how thoroughly tests have exercised recent code changes, letting the TA focus effort on especially error-prone areas — new, untested changes — rather than all low-coverage areas, including code unchanged and already tested for prior releases.

Defect arrival pattern analysis

Compares the number or density of defects found across successive project phases (e.g. iterations) against theoretical distribution patterns, revealing the strength of existing test cases and room for improvement.

Example

A classic defect arrival pattern is the Rayleigh model: a single peak skewed to the right, where the expected number of defects found rises over time, peaks, then drops slowly toward zero. If defect detection stays flat and low when the pattern suggests it should be rising, the existing tests may be too weak to detect additional defects.

These analyses rely on defect-related metrics — number of defects, DDP, and others — calculated from test results (e.g. tests passed/failed), defect reports, and structural metrics (e.g. code coverage, defect density). But these metrics are not always as straightforward to read as they seem: the number of failed tests is not necessarily the number of defects detected, since the relation between test results and defects can be many-to-many — several tests may detect the same defect, or one test may detect several defects. The severity of a defect may also differ from the criticality of the test that found it, as a critical test case can fail because of a cosmetic defect. Calculating the actual number of defects detected requires carefully analyzing the results of the debugging process.

5.3.2 Supporting Root Cause Analysis with Defect Classification K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic, and can summarize, compare, classify, and give examples for the concept.

Root cause analysis (RCA) identifies and addresses the underlying causes of a defect rather than only its symptoms. It supports a structured approach to quality improvement, with preventing defect recurrence as its primary objective. The TA uses various techniques to identify root causes of defects and failures — for example, defect taxonomies, the five whys technique, cause-effect diagrams, and Pareto analysis.

Classical RCA has subject matter experts study a resolved defect in considerable detail. But with many defects to analyze, planning preventive action for each one individually is inefficient and time-consuming. Defect classification addresses this: classifying defects first, then performing RCA on the defect types that occur, rather than on every individual defect.

Defect classification rests on the recognition that individual defects capture a great deal of information about the development process and the system under test. It lets the TA extract that information and turn it into a process measurement, giving insight into the types of errors made during development — useful for process improvement. Classification bridges quantitative defect statistics and qualitative RCA. To effectively support RCA, defects should be classified uniformly across the entire SDLC, from early testing through production. The TA should also support the organization in standardizing defect classification, improving communication and information exchange about defects among developers and organizations, and thereby facilitating RCA.

Orthogonal defect classification (ODC)

Classifies each defect into orthogonal — mutually exclusive — attributes, collected both when a defect is reported and when it is fixed.

IEEE 1044

A standard classification for software anomalies, providing a core set of attributes for classifying failures and defects.

Severity-based classification

Classifies defects by severity — for example, critical, major, minor, trivial.

Defect taxonomy models

Structured taxonomies used as an alternative basis for classifying defects.

Note

Defects can also be mapped to quality attributes using software quality models such as ISO/IEC 25010 or the FURPS model.

1.1

Principles of Performance Testing K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic.

Performance efficiency — often shortened to “performance” — is essential to a good user experience, and performance testing establishes acceptable quality levels for end users. It applies well beyond web applications, to client-server, distributed and embedded architectures alike. ISO 25010 categorizes performance efficiency as a non-functional quality characteristic with three sub-characteristics:

Time behavior

The most common objective: can the system respond to inputs within a specified time and conditions? Ranges from end-to-end response time to CPU cycles for one task.

Resource utilization

Investigated when availability of system resources (e.g. RAM allocation) is identified as a risk.

Capacity

Evaluated when system behavior at required capacity limits — users, data volumes — is a risk to the architecture.

All three sub-characteristics affect the system under test’s ability to scale.

Performance testing is often experimental: measurement and analysis of system parameters, conducted iteratively to support architectural decisions and shape stakeholder expectations. Five principles keep it useful:

  1. 1

    Aligned to stakeholder expectations

    Tests must reflect what users, system designers and operations staff actually expect.

  2. 2

    Reproducible

    Repeating a test on an unchanged system must yield statistically identical results within a defined tolerance.

  3. 3

    Understandable & comparable

    Results must be interpretable and readily compared against stakeholder expectations.

  4. 4

    Representative

    Run on complete or partial systems/environments that represent production, where resources allow.

  5. 5

    Affordable & executable

    Practically achievable within the timeframe the project sets.

Types of Performance Testing K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic.

Different types of performance testing apply depending on the objectives of a given project.

Load testing

Anticipated realistic loads from controlled numbers of concurrent users or processes.

Stress testing

Peak loads at or beyond specified limits; also reduced availability of resources like bandwidth or memory.

Scalability testing

Future efficiency requirements — growth in users or data — without violating current requirements.

Spike testing

Sudden bursts of peak load, and a correct return to steady state afterward.

Endurance testing

Stability over an operationally relevant time frame — memory leaks, DB connections, thread pools.

Concurrency testing

Simultaneous actions (e.g. mass login); notoriously hard to find and reproduce, especially in production.

Capacity testing

How many users/transactions the system supports while still meeting performance objectives.

Performance Measurement Fundamentals

Performance testing lives or dies on its metrics. This chapter covers why measurements matter, how to collect and select the right ones, how to aggregate them for different audiences, where they come from, and what a typical performance test actually produces.

  • measurementThe process of assigning a number or category to an entity to describe an attribute of that entity.
  • metricA measurement scale and the method used for measurement.

2.1

Typical Metrics Collected in Performance Testing K2K2: UnderstandThe candidate can select the reasons or explanations for statements related to the topic.

2.1.1 Why Performance Metrics are Needed

Performance testing shouldn’t start before deciding which measurements and metrics matter. Skip this and the risks pile up:

Unknown whether performance levels meet operational objectives.

Requirements never defined in measurable terms.

No way to spot trends predicting lower performance.

No baseline to compare actual results against.

Results judged by subjective opinion instead of data.

Tool output goes misunderstood.

2.1.2 Collecting Performance Measurements and Metrics

Metrics chosen vary with business context (processes, user behavior, stakeholder expectations), operational context (technology and its use), and test objectives — an e-commerce site and an embedded medical device need very different metrics. A common way to categorize them is by technical, business, or operational environment.

EnvironmentTypical metrics
TechnicalResponse time, resource utilization (CPU, memory, bandwidth, latency, disk, I/O, threads), transaction throughput, batch processing time, error counts, completion time, background load, code complexity.
BusinessBusiness process efficiency, throughput of transactions/work, SLA compliance, scope and concurrency of usage, timing of usage (e.g. peak-hour order volume).
OperationalOperational process timing (start-up, backup, shutdown), system restoration time, time to issue alerts/warnings.

2.1.3 Selecting Performance Metrics

Collecting more metrics than needed isn’t free — each one needs consistent collection and reporting. The Goal-Question-Metric (GQM) approach helps: establish goals, ask questions that reveal whether they’re met, then attach a measurable metric to each question. GQM doesn’t fit every case — some metrics describe system health without linking to a specific goal. Expect to add further measurements as initial results reveal what’s really needed.

2.2

Aggregating Results from Performance Testing K2K2: UnderstandThe candidate can explain why results from performance testing are aggregated.

Viewed only at the detailed level, performance metrics can be hard to draw the right conclusion from — especially for business stakeholders, whose main concern is usually just whether response time stays within acceptable limits. Aggregating detailed metrics lets:

Business and project stakeholders see the “big picture” status.

Performance trends become visible.

Categories of Performance Risks for Different Architectures K2K2: UnderstandThe candidate can explain typical categories of performance risks for different architectures.

Performance risk varies considerably with architecture, application and host environment. A system can combine several architectures at once, in which case all their risks apply.

Single computer

Excessive resource consumption (leaks, background activity, slow storage), inefficient algorithms.

Multi-tier

Each server carries single-computer risks, plus poor/non-scalable database design and network bottlenecks.

Distributed

Multi-tier risks plus unreliable or unpredictable remote servers under periodic load or connection problems.

Virtualized

Excessive load across virtual machines sharing hardware, or misconfigured host resources.

Dynamic / cloud-based

Self-scaling mitigates some risk, but misconfiguration of that scaling at setup or update is itself a risk.

Client–server

Client-side single-computer risks plus connection speed/reliability, network congestion, firewalls and load balancing.

Mobile applications

Limited, variable device resources and connectivity; heavy interaction with local apps and remote services.

Embedded real-time

Similar risks to mobile, but consequences can be safety-critical (e.g. a vehicle braking system).

Mainframe

Predictable when used as designed, but new API/web-service access paths can introduce unexpected load.

Beyond architecture

Language choice (e.g. manual heap management in C/C++), relational vs. non-relational databases, even recursive vs. iterative algorithms all shape performance risk — down to individual function design.

3.3

Performance Risks Across the Software Development Lifecycle K4K4: AnalyzeThe candidate can analyze performance risks for a given product across the software development lifecycle.

Performance-related quality risk analysis follows the general risk process, focused on time behavior, resource utilization and capacity:

  1. 1

    Identify risks

    To product quality, focused on the three performance efficiency sub-characteristics.

  2. 2

    Assess

    Cover the relevant architecture categories (3.2); evaluate likelihood and impact with clear criteria.

  3. 3

    Mitigate

    Take action appropriate to the nature and level of each risk.

  4. 4

    Manage ongoing

    Keep risks adequately mitigated right up to release.

Business stakeholders bring awareness of how performance problems affect customers and the business (financial, reputational, legal exposure); technical stakeholders bring understanding of how requirements, architecture, design and implementation choices create the risk in the first place. Both perspectives are needed.

Start early, repeat often

Relying only on performance testing late in system or system integration test level invites unpleasant late-project surprises. A careful technical review (e.g. of database design by experienced engineers) can predict problems before implementation even happens — risk analysis should be iterative across the whole SDLC, not a one-off gate.

Report residual risk precisely

“Yes, delays are still possible at checkout” tells stakeholders nothing useful. Reporting the percentage of customers likely to see delays past a given threshold does.

4.1.1 Deriving Performance Test Objectives

Stakeholders set objectives, terminology, and criteria for “achieved.” It helps to separate user-based objectives (end-user satisfaction, business goals — users mostly just want to get their task done) from technical objectives (scalability, the conditions under which degradation appears). Gathering information means asking: what transactions run and what response time is expected, which system metrics are captured and to what target, and what improvement is expected versus prior test cycles.

4.1.2 The Performance Test Plan

Acceptance criteria

Tied to objectives, SLAs, and baseline values — a set of metrics for comparing current against prior results.

Test data

System configuration

Architecture, tiers, hardware/software details and versions, external system integrations, SUT build/version.

Test environment

How it maps to production, and how results will be extrapolated if it’s scaled down.

Test tools

Tools (and versions) for simulating transactions, generating load from multiple points, and monitoring.

4.1.3 Communicating about Performance Testing

What to emphasize depends on the audience.

Business-focused stakeholders

Less interested in functional/non-functional distinctions or tooling detail; care about the link between product risk and test objectives, cost vs. representativeness trade-offs, repeatability, project risks/dependencies, and a broad plan with costs and milestones.

Technology-focused stakeholders

Need the load-profile generation approach explained, detailed setup/execution steps tied to architectural risk, repeatability steps, environment-sharing schedules, mitigations if testing must run in production, and clarity on their own tasks and timing.

4.2

Analysis, Design and Implementation K4K4: AnalyzeAnalyze operational profiles, create load profiles, analyze throughput and concurrency, implement scripts.

4.2.1 Typical Communication Protocols

Designing tests that target the right part of the system means understanding protocols, usually described via the OSI model. Performance testing most often works at Layer 5–7 (Session–Application):

Database

ODBC, JDBC, other vendor-specific protocols.

Web

HTTP, HTTPS, HTML.

Web service

SOAP, REST.

Network, mobile, remote access, SOA

E.g. DNS/FTP/SMTP, TruClient/SMS/MMS, Citrix ICA/RTE, MQSeries/JSON/WSCL.

Which layer matters most tracks the architecture level being tested — low-level embedded systems push focus toward lower OSI layers.

4.2.2 Transactions

A transaction is the set of activities from initiation to completion of one or more requests/operations; its response time is a core performance measurement. Simulated transactions can include think time to mimic real user pacing — response time plus think time is the transaction’s elapsed time. Ramping up load while tracking transaction times helps correlate degradation with specific transactions. Transactions can also be nested, so a discrete step (e.g. add item to cart) and the whole flow (complete order) are both measurable from one test.

4.2.3 Identifying Operational Profiles

Multiple operational profiles may exist for one application, later combined into a load profile. Building them follows three steps:

  1. 1

    Identify the data

    User personas/roles, generic tasks (modeled at a high level, e.g. business processes), estimated user counts per role/task over time.

  2. 2

    Gather the data

    Stakeholder interviews/workshops, functional specs and user stories (“As a <user>, I want…” directly names user types), usage data from similar or current systems, and observed user behavior (ideally coordinated with usability testing).

  3. 3

    Construct the profiles

    Top-down: start broad, break down only as needed; single out profiles that are frequent, high-risk, or data-heavy; review and refine with stakeholders before building load profiles.

Not just interactive users

Off-line batch systems need operational profiles focused on throughput and completion within a time window; systems of systems need profiles modeling input from other systems or components, sometimes requiring detailed buffer/queue analysis with architects.

4.2.4 Creating Load Profiles

A load profile needs: the test objective (e.g. evaluate behavior under stress), accurate operational profiles, known throughput/concurrency issues, and the quantity/timing with which profiles execute — typically as ramp-ups, ramp-downs, steps (instantaneous jumps), or predefined distributions mimicking daily/seasonal cycles.

Example

A stress load profile might combine a flat step of 100 virtual users running Operational Profile 1 for the whole test (a background load) with a ramp-up to 220 virtual users on Operational Profile 2, held for two hours, then ramped down — together subjecting the system to a three-hour stress window.

4.2.5 Analyzing Throughput and Concurrency

System throughput is the number of transactions of a given type processed per unit time (distinct from network throughput, the data volume moved). Load is often defined by concurrent user count instead — easier to state, and how load-testing tools define load — but without knowing what each user is doing and how intensely, user count alone is a poor measure of load.

Same users, 60× the load

500 users running short queries once a minute yields 30,000 queries/hour. The same 500 users running one query per hour yields 500 queries/hour — 60× less load and hardware demand, from an identical user count.

System throughput = [virtual users] ÷ ([processing time] + [think time])

Concurrency is the number of simultaneous/parallel threads or users, usually modeled by setting the virtual user count. Even at equal throughput, concurrency changes resource use, since each parallel session holds its own resources. Most test setups are closed systems (fixed user population, from queuing theory) whereas many public systems are open — new users keep arriving regardless of whether current ones are still waiting.

4.2.6 Basic Structure of a Performance Test Script

A script simulates user or component activity, issuing requests in proper order and pace. It can be built by recording at the protocol level (parameterized and replayed), recording at the GUI level (captured then run at scale via a load generation tool), or programmed directly against protocol requests, GUI actions, or API calls. Structurally, scripts typically have an initialization section, a repeatable main section, and a clean-up section, plus timers for response-time data (protocol-level scripts measure server/network time; GUI scripts measure end-to-end time), verification/error handling (default tool checks are often minimal), and synchronization points to coordinate concurrent actions across scripts.

4.2.7 Implementing Performance Test Scripts

Scripts are implemented from the PTP and load profiles, usually simulating one operational profile per script (sometimes combined via conditional logic). Recording simulates the real system closely; programming relies on knowing the correct request sequence. After protocol-level recording, correlation — replacing recorded internal identifiers with variables extracted from responses — is essential; incorrect or missing correlation is the main reason recorded scripts fail on replay.

Don’t reuse one user’s data

Running many virtual users against the same recorded user/data set gives misleading results in both directions: data may be fully cached (unrealistically fast), or locking may serialize updates (unrealistically slow). Scripts and data need proper parameterization so each virtual user has a distinct, representative data set.

Think times are inserted or adjusted to match the intended throughput (4.2.5); scripts for separate operational profiles are then combined into a scenario that the load profile controls — how many virtual users each script starts, when, and with what parameters.

4.2.8 Preparing for Performance Test Execution

Preparation covers setting up the system under test, deploying the environment, and configuring load generation and monitoring so all needed data gets captured. The closer the environment is to production, the more reliable the projection to production performance — performance is a non-linear function of environment fidelity, so gaps compound quickly.

Data

Size and structure strongly affect results; test data should match production in size and structure as closely as possible, and be restorable between cycles.

Service virtualization

Stubs emulate unavailable components (e.g. a third-party payment processor), isolating the SUT.

Deployment options

Internal/external test labs, cloud IaaS, or cloud SaaS load-testing services — choice depends on whether the goal is isolating small variations, whole-production load testing, or minimizing cost.

Configuration & network emulation

Match production configuration where possible (e.g. adjust memory parameters if test hardware has less RAM); emulate network conditions for global or mobile systems.

Load generators themselves need monitoring — a slow generator can silently under-deliver the intended load. Before real tests run, validate the environment and setup with a controlled test run.

4.3

Execution K2K2: UnderstandUnderstand the principal activities in running performance test scripts.

Execution generates load per the load profile, monitors the environment, and collects results — usually automated by the load-testing tool once properly configured. Tests generally target a steady state: the period once all simulated users/threads are running as designed. The transition into it is the ramp-up, the transition out is the ramp-down; both are harder to monitor and analyze than the steady state itself, and standard approaches like monitoring averages can be misleading during them — relevant for spike tests or mass concurrent logins.

While it runs

Define how failures are handled (e.g. logging a failed user out to release its resources); time-synchronize all monitoring/log-analysis tools; watch the console and logs in real time to catch problems early — large-scale performance tests are expensive to run to the end unnecessarily. One verification technique: run functional GUI-level scripts in parallel with a protocol-level load test, to confirm response times only differ by client-side overhead.

In CI, checks must run automatically since manual monitoring may not be possible — easier for regression performance tests with well-understood behavior than for exploratory or large-scale tests needing dynamic adjustment.

4.4

Analyzing Results and Reporting K4K4: AnalyzeAnalyze and report performance test results and implications.

Data is compared against the PTP’s defined metrics; conclusions feed a summary report with recommended actions (hardware/routing changes, software optimization, network changes). Typically analyzed:

Simulated user status

Checked first — errors here can distort every other metric.

Transaction response time

Min/max/average/90th percentile; average alone is easily skewed by outliers, and 100% compliance is rarely worth its cost.

Transactions per second

System throughput — how much work got done.

Transaction failures

Always worth investigating; can also distort transactions-per-second data.

Hits & network throughput per second

Server hit rate; data volume received by simulated users.

HTTP responses

By response code, per second.

Techniques include comparing to requirements, observing trends, statistical quality control, error identification, and comparing to prior test results. Correlating metrics (e.g. at what throughput did CPU hit 90% and the system slow down?) helps find the root cause behind degradation, which confirmation testing then validates as fixed.

Executive summary

Concise, actionable conclusions once all analysis is complete.

Test results

Baseline snapshot, architecture diagram, detailed tables/charts of response time, transaction rate, error rate.

Test logs

Start time, duration, scripts and config used, data files, HW/SW config, CPU/RAM utilization, defects.

1.1

Generative AI Foundations and Key Concepts K2K2: UnderstandExplain the basics of generative AI and LLMs; distinguish LLM categories.

Generative AI (GenAI) is a branch of AI that uses large, pre-trained models to generate human-like text, images or code. Large language models (LLMs) are pre-trained on huge textual datasets, letting them determine context and produce relevant responses to prompts. In software testing, LLMs can support reviewing acceptance criteria, generating test cases or scripts, identifying potential defects, analyzing defect patterns, generating synthetic test data, and supporting documentation — across the whole test process.

1.1.1 AI Spectrum: Symbolic AI, Classical Machine Learning, Deep Learning, and Generative AI

Symbolic AI

Rule-based; represents knowledge with symbols and logical rules to mimic human decision-making.

Classical machine learning

Data-driven: data preparation, feature selection, model training — e.g. defect categorization, predicting software problems.

Deep learning

Neural networks that automatically learn features from large, complex data — images, video, audio, text — though tuning and validation still need human involvement.

Generative AI

Uses deep learning to create new content by learning and mimicking training-data patterns; LLMs can generate text, write code, and simulate reasoning within their training scope.

GenAI’s key advantage for testing: pre-trained models apply directly to test tasks with no extra training phase — though that comes with risks (see chapter 3).

1.1.2 Basics of Generative AI and LLMs

LLMs are built on the generative pre-trained transformer model and trained on very large datasets — books, articles, websites. Small language models (SLMs) are compact, lighter-weight alternatives with fewer parameters. Two concepts convert language into a form an LLM can process: tokenization (breaking text into tokens, from characters to sub-words to whole words) and embeddings (numerical vectors encoding a token’s meaning, positioning similar tokens close together in a high-dimensional space). The transformer architecture processes long text sequences and predicts the next token during inference — producing text that is statistically plausible, not necessarily correct.

Non-determinism

LLMs behave non-deterministically because of the probabilistic nature of inference and hyperparameter settings — the same input can produce different outputs across runs (see 3.1.4 for mitigation).

Context window

The amount of preceding text (in tokens) an LLM can consider. A larger window keeps coherence over longer passages (e.g. large test logs), but costs more compute and processing time.

1.1.4 Multimodal LLMs and Vision-Language Models

Multimodal LLMs extend the transformer to process text, images, sound and video together, adapting tokenization per data type — images, for instance, are converted to embeddings via vision-language models before entering the transformer. In testing, this lets an LLM analyze screenshots or GUI wireframes alongside textual defect reports or user stories, spotting discrepancies between expected and actual visuals, and generating richer test cases that combine text and visual cues.

2.1.1 Structure of Prompts for Generative AI in Software Testing

A structured prompt for software testing typically has six components:

Role

The persona the model adopts — e.g. tester, test manager, automation engineer — shaping tone and responsibilities.

Context

Background the model needs: the test object, functionality under test, relevant surrounding detail.

Instruction

A clear, imperative, concise description of the task and its requirements.

Input data

User stories, acceptance criteria, screenshots, code, existing test cases, output examples.

Constraints

Restrictions or special considerations governing how instructions apply to the input data.

Output format

The expected format, structure or characteristics of the response.

2.1.2 Core Prompting Techniques for Software Testing

Three techniques are commonly combined with the 6-component structure above:

Prompt chaining

Breaks a task into intermediate steps, each checked/refined before the next — greater accuracy for complex, decomposable tasks.

Few-shot prompting

Gives the model examples. Zero-shot gives none; one-shot gives one; few-shot gives several, to consolidate the desired pattern.

Meta prompting

The LLM generates or refines its own prompts, iteratively evaluated by the tester — a form of pairing that reduces manual prompt-crafting effort.

These techniques combine well — e.g. meta prompting to draft an initial prompt, few-shot to lock in a pattern, then prompt chaining to validate each step (see 2.2.5).

3.1

Hallucinations, Reasoning Errors and Biases K3K3: ApplyIdentify hallucinations, reasoning errors and biases in LLM output; summarize mitigation techniques.

LLMs are prone to specific defects that degrade the quality of test-task output. Non-determinism (1.1.2) makes them slippery to fix — a defect that appears gone in one conversation can reappear in another with the same model.

3.1.1 Hallucinations, Reasoning Errors and Biases in Generative AI

Hallucinations

Factually incorrect or irrelevant output — fictitious test cases, broken scripts, tests for acceptance criteria that don’t exist.

Reasoning errors

LLMs pattern-match rather than truly reason logically, so cause-effect, conditional logic and multi-step problems (e.g. test planning, prioritization) can go wrong.

Biases

Rooted in training data; can skew generated test data or acceptance-criteria refinement toward overrepresented patterns (e.g. English-language assumptions).

3.1.2 Identify Hallucinations, Reasoning Errors and Biases in LLM Output

Defect typeDetection approaches
HallucinationCross-verification against documentation/requirements; domain expert consultation; consistency checks across outputs.
Reasoning errorLogical validation of the generated content’s coherence; output testing — run the generated test cases/scripts and check results.
BiasReview whether generated testware fairly represents the test strategy and coverage; check for underrepresented test types.

How rigorously to detect these is a risk-based call, matched to the estimated risk level of the test task.

3.1.3 Mitigation techniques of GenAI hallucinations, reasoning errors and biases in software test tasks

Provide complete context in the prompt — missing information is a common root cause.

Split complex prompts via prompt chaining, verifying each step before the next.

Use clear, structured, unambiguous data formats.

Select an LLM actually suited to the task (see 5.1.3).

Compare results across multiple LLMs to catch outliers.

Chapter 4 introduces two more complementary techniques: Retrieval-Augmented Generation and fine-tuning.

3.1.4 Mitigation of Non-Deterministic Behavior of LLMs

Non-determinism comes from probabilistic sampling during inference, and gets worse for longer outputs.

Lower the temperature

Narrows the probability distribution for more consistent output — at the cost of creativity and diversity.

Set a random seed

Where supported, fixes the pseudo-random sequence used, improving reproducibility.

4.1.1 Key Architectural Components and Concepts of LLM-Powered Test Infrastructure

Unlike a conversational chatbot, an LLM-powered test tool processes test-related queries, analyzes requirements, generates test cases, and evaluates outputs. Its architecture typically has three layers:

Front-end

Where testers input queries or commands.

Back-end

Handles authentication, data retrieval, prompt preparation, and interaction with the LLM — and post-processes its output to align with test conditions.

LLM

Hosted third-party (via API) or a custom in-house model; the smart processing component that reasons over testware, not just a server.

The back-end typically integrates both relational databases (structured data like test cases) and vector databases (semantic retrieval via embeddings).

4.1.2 Retrieval-Augmented Generation

Retrieval-Augmented Generation (RAG) grounds LLM responses in additional data sources rather than relying solely on pre-existing training. Documents are chunked (e.g. 256–512 tokens), cleaned, and encoded into embeddings stored in a vector database.

RetrievalFind chunks matching the query by semantic similarity
→
GenerationLLM combines retrieved chunks with its own knowledge

For testing, RAG lets LLM-powered infrastructure reach into an organization’s own databases, documentation and repositories in real time — keeping test analysis or design aligned with the latest specifications and requirements, not just what the model was originally trained on.

4.1.3 The Role of LLM-Powered Agents in Automating Test processes

LLM-powered agents go beyond question-response: they can “act” by invoking predefined functions (“tools”) to interact with external systems.

Autonomous agents

Operate independently with minimal human intervention, using predefined rules and adaptive feedback loops.

Semi-autonomous agents

Perform tasks with periodic human oversight to keep output aligned with defined goals.

Multi-agent architectures coordinate several specialized agents — called orchestration — automating tasks across the whole test lifecycle: test analysis, design, implementation, execution and reporting, shifting automation from script-based execution toward goal-driven, agent-based automation.

Same risks apply

Agents can still hallucinate, reason incorrectly, or carry bias (3.1) — mitigated with automated verification of their results, or by keeping critical tasks semi-autonomous.

4.2.1 Fine-Tuning LLMs for Test tasks

Fine-tuning further trains a pre-trained LLM or SLM on a targeted dataset, teaching it domain-specific knowledge, vocabulary and reasoning. For example, training on an organization’s own user stories and test cases aligns the model with that organization’s process and terminology. SLMs (smaller, less resource-intensive) can be fine-tuned for high performance on a specific task without an LLM’s computational overhead.

Data quality

Biased or low-quality training data produces biased or inaccurate fine-tuned output.

Overfitting

Over-specialization to training data hurts generalization to new, unseen situations.

Opacity

Lack of transparency into the model’s reasoning complicates debugging and validation.

Compute cost

Fine-tuning an LLM (less so an SLM) demands significant computational resources.

4.2.2 LLMOps when Deploying and Managing LLMs for Software Testing

AI chatbot

Test tool with GenAI capability

Similar concerns, plus evaluating the tool vendor’s own data security and performance assurances.

In-house GenAI test tool

Full control over privacy/security, but requires real expertise, resource planning, and validation processes of its own.

These approaches aren’t mutually exclusive — an organization might mix a chatbot for some tasks with custom in-house tools for others, layering in RAG and fine-tuning as needed.

A hands-on approach works best: practicing with real LLMs/SLMs, following structured learning paths, and building know-how gradually through internal sharing.
