Testing Quality Characteristics

This chapter uses the software quality model of ISO 25010 as a guide to the quality characteristics in focus for a test analyst (TA), though its usability terminology follows the Usability Testing Syllabus instead. It covers functional suitability, usability, flexibility, and compatibility — and how the TA contributes to testing each.

  • adaptabilityA sub-characteristic of flexibility testing that verifies the test object can be adapted for or transferred to intended target hardware, software, or other operational environments.
  • compatibilityA quality characteristic verifying whether a test object works correctly with other components or systems when used, split into interoperability and coexistence.
  • flexibilityAlso known as portability; verifies that the test object can be adapted to changes in its context of use or system environment, covering adaptability, scalability, installability, and replaceability.
  • functional appropriatenessTesting that verifies the functions facilitate accomplishing specified tasks and objectives, focusing on whether everything implemented fulfills users' needs.
  • functional completenessTesting that covers all specified tasks and intended users' objectives, asking whether everything that is asked for is implemented.
  • functional correctnessTesting that answers whether actual results are correct — accurate, precise, and consistent — for valid and invalid inputs.
  • functional suitabilityThe ISO 25010 quality characteristic covering functional completeness, functional correctness, and functional appropriateness.
  • functional testingOne of the core tasks of the TA, addressing the three sub-characteristics of functional suitability using appropriate test levels and techniques.
  • installabilityA sub-characteristic of flexibility that verifies the test object can be installed, uninstalled, updated, and reconfigured correctly in specified environments.
  • interaction capabilityA usability aspect covering how the product enables users to complete tasks in specific contexts of use effectively, efficiently, and satisfactorily.

  • user experienceA usability aspect addressing users' perceptions before, during, and after interacting with the test object.

4.1

Functional Testing

Functional testing is one of the TA's core tasks. The ISO 25010 product quality model splits functional suitability into three sub-characteristics — functional completeness, functional correctness, and functional appropriateness. All three can be assessed by functional testing, but not every test activity addresses them equally well, so the TA must select the test levels and techniques that fit each sub-characteristic's product risks.

4.1.1 Functional Completeness Testing K2

Functional completeness testing should cover all specified tasks of the software and the intended users' objectives. The key question: is everything that is asked for implemented?

It should be addressed as early as possible — by reviewing the requirements specification in sequential development models, or by discussing user stories and their acceptance criteria during collaborative user story writing in Agile. In system testing, system integration testing, and acceptance testing, it can also be tested dynamically. Behavior-based techniques such as scenario-based testing fit well, though other black-box techniques are suitable too. Traceability between test basis, test conditions, and test cases is essential to determine the level of functional completeness achieved.

4.1.2 Functional Correctness Testing K2

Functional correctness testing answers whether actual results are correct — accurate, precise, and consistent — for valid and invalid inputs. Finding an effective test oracle that provides expected results in detail is crucial.

It can be tested at any test level, but in the spirit of shift left, most functional correctness testing should occur in component testing and component integration testing. Even where the TA is not responsible for these levels, the TA should still contribute to best achieve the test objectives. All black-box techniques, experience-based techniques, and collaboration-based testing are suitable.

4.1.3 Functional Appropriateness Testing K2

Functional appropriateness testing verifies that the functions facilitate accomplishing specified tasks and objectives. The focus is on whether everything implemented fulfills users' needs.

It may include user interface design reviews, especially for interactive applications. Dynamic testing starts with system testing and acceptance testing in sequential models, or with demo sessions in Agile. Exploratory testing and collaboration-based testing are most appropriate, and behavior-based black-box techniques are also suitable.

Key distinction

Completeness asks whether everything required is built; correctness asks whether the results are right; appropriateness asks whether what was built actually helps users accomplish their tasks.

4.2

Usability Testing

Usability refers to a broad concept of user-related quality characteristics, covering interaction capability from the ISO 25010 product quality model and beneficialness from the ISO 25019 quality-in-use model.

4.2.1 Aspects of Usability K2

Usability testing usually focuses on evaluating three aspects:

Interaction capability

Enabling users to complete tasks in specific contexts of use effectively, efficiently, and satisfactorily.

User experience

Addressing users' perceptions before, during, and after interacting with the test object.

Accessibility

Ensuring users with disabilities, diverse cultural backgrounds, or language barriers can use the system effectively and efficiently.

The TA can collaborate in usability testing from an early phase using their knowledge of the target user groups, their goals, their context of use, potential difficulties using the system, or negative user experience.

4.2.2 Usability Evaluation Techniques K2

The TA contributes to three principal usability evaluation techniques:

Usability reviews

Performed by usability experts to identify potential usability problems and deviations from established criteria, ranging from informal reviews to inspections. The TA adapts review criteria to the specific user groups, business objectives and priorities, and context of use — e.g. tailoring a generic usability checklist.

Usability test sessions

Future users or their representatives try to solve predefined tasks to evaluate whether tasks can be completed effectively, efficiently, and satisfactorily. The TA may help design scenarios for these sessions according to personas, user groups, or operational profiles.

User questionnaires or surveys

Including rating and feedback, these measure user satisfaction (e.g. SUMI and WAMMI). The TA can help design a questionnaire and evaluate responses against the specific goals of the targeted users within their context of use.

4.2.3 Accessibility Testing

A common test objective in accessibility testing is to verify compliance with standards.

Note

The international standard Web Content Accessibility Guidelines (WCAG) defines three levels of conformance — A, AA, and AAA — representing increasing degrees of web content accessibility. National standards include the United Kingdom's Equality Act and the United States' Americans with Disabilities Act. The TA identifies the required compliance level and the specific needs of the intended target group by analyzing the context of use.

4.3

Flexibility Testing

Flexibility testing (also known as portability testing) verifies that the test object can be adapted to changes in its context of use or system environment. The ISO 25010 product quality model differentiates four sub-characteristics of flexibility, with both technical and non-technical aspects.

4.3.1 Adaptability Testing K2

Adaptability testing verifies that the test object can be adapted for or transferred to the intended target hardware, software, or other operational or usage environments.

The TA supports adaptability testing by identifying the intended target environments (e.g. versions of mobile operating systems supported, versions of browsers that may be used) and designing tests that cover combinations of these environments. Because this requires test data representing various environment parameter configurations, combinatorial testing is often applied. Another example is integrating various platform components into customer projects to ensure compatibility across target environments. Depending on product risk, the TA designs and executes smoke tests or a more comprehensive test suite to verify correct adaptation to the target environment.

Example

By following adaptability testing good practices — defining target environments early, using combinatorial testing, smoke testing on new environments, and monitoring environment-specific defects — the TA can uncover defects that could limit the software's lifespan and usability (e.g. ease of use on different screen sizes). This work should also be supported by automated cross-platform testing implemented by test automation engineers. Rigorous adaptability testing detects environment-specific issues early, helping avoid frequent major updates or redesigns after deployment and lowering maintenance costs.

4.3.2 Installability Testing K2

Installability testing verifies that the test object can be installed, uninstalled, updated, and reconfigured correctly in specified environments. It extends beyond merely checking that the installation procedure runs to completion. Typical installability test objectives for the TA:

Verify correct execution under configurations

Confirm installation procedures execute correctly under various environment parameter configurations — combinatorial testing helps here, similar to adaptability testing.

Verify post-install/update behavior

Design and execute tests to determine whether the test object works properly after installation or update.

Check ease of install/uninstall/update

Assess how easy it is for users to install, uninstall, or update the software, including reviewing the installation documentation.

Test permissions-related behavior

Particularly important for mobile applications.

4.4

Compatibility Testing

Compatibility testing verifies whether a test object is compatible with other components or systems when it is used. The ISO 25010 product quality model differentiates two sub-characteristics of compatibility, giving two compatibility test types.

In this chapter

Interoperability testing

Verifies compatibility with components or systems the test object is intended to interact with. Typically black-box functional tests, so the TA is usually responsible.

Covered elsewhere

Coexistence testing

Verifies the test object can share its target environment with other components or systems without interference. A technical test type discussed in the Technical Test Analyst syllabus.

4.4.1 Interoperability Testing K2

The goal of interoperability testing is to verify that two or more components or systems can exchange information and mutually use the information that has been exchanged. When the exchange involves a data transformation, interoperability testing must include verification of that transformation.

Interoperability testing is particularly important when multiple systems need to collaborate, share data, or perform tasks together — especially in modern architectures such as cloud solutions, web services, microservices, containerization, and the Internet of Things. Interoperability usually happens across various architectural levels; the TA must understand the possible interactions to define proper test conditions. Not all interactions may be documented, so the TA may need to retrieve information indirectly from architecture and design documentation — understanding this documentation is crucial to ensure all important aspects of the interactions get tested.

Data transformation defects

Errors in transformations applied during the exchange of data.

Interpretation or use defects

Errors in how exchanged data is interpreted or used.

Communication defects

Errors in communication flows and protocols between systems.

Standards compliance defects

Failures to comply with relevant standards.

End-to-end functionality defects

Failures in functionality that spans the full interaction chain.

Design documentation defects

Errors or gaps discovered in the design documentation itself.

Interoperability testing is usually applied during integration testing. Suitable black-box techniques include data-based techniques focused on the exchanged data, behavior-based techniques for interpreting or using the data, and end-to-end functionality or rule-based techniques for data transformation. Experience-based techniques can usefully complement black-box testing.

Watch out

Test cases from functional testing or adaptability testing may be reused for interoperability testing — don't build a separate suite from scratch if existing cases already exercise the relevant interactions.
